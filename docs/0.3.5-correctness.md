# 0.3.5 — Draft session correctness

Historical scope: retain the macro placeholder fix (Task 13) and address R1–R4 from the 2026-10-27 review. These changes did not alter qualification, transport ACK handling, the Fn write gate, or hardware feature availability. The live 0.3.4 deployment and 0.3.5 source were separate release states. The current project release is **0.4.0-beta.1**.

## R1 — Invalid input and editor context

Previously, refreshing after a field error restored every control value, carrying an old layer and binding into a new selection. The editor now retains the invalid input with a fingerprint of its layer, key set, draft, and edit permissions. Invalid values are restored only while that fingerprint matches; binding and layer always follow the model. Changing keys or layers, mixed/empty selections, valid edits, and Revert discard the old error context. Invalid input creates no session changes.

## R2 — Macro allocation ownership

Pointers describe live allocations only. Inferring free space from current pointers made bytes previously generated by the app become opaque after relocation, causing false capacity failures. Nonzero or unreferenced byte patterns are not evidence that data can be erased.

Each ConfigSession keeps a private allocator closure tied to a baseline copy. Reusable bytes are established from:

- Zero baseline bytes in body span 400–1023.
- Decoded semantic channels in bodies referenced by baseline pointers.
- Exclusion of nonzero reserved bytes and bytes containing opaque flag bits (`flags & 95`).

New allocations write only into this established set, or retain a body in place while preserving reserved/opaque bits. The two action/device bits remain editable. Live macro metadata comes from the current source; fabricated reserved bytes/flags from profiles are not accepted. When app-used regions lose references or shrink, only owned bytes return to their baseline values; opaque anchors remain intact. Such regions remain reusable even without a pointer. Other macros and the pointer table are planned before results are written.

The planner prefers stable pointers and in-place growth. If that fragments capacity, it tries compaction in descending size order within regions established as safe, keeping bodies with captured anchors in place where valid. If no suitable contiguous layout exists, the operation fails atomically. Total free bytes do not guarantee that every fragmented/opaque layout can fit a large body; unknown data is never erased to force a fit.

### Lifecycle

- Ownership derives from an immutable baseline. Failed planning consumes no space and changes neither draft nor diff. Lazy decoding happens only on macro edits, so an opaque macro capture does not prevent reading/editing other blocks.
- Preview uses a shadow session sharing the current session's immutable closure. It neither reconstructs permissions from draft bytes lacking history nor changes the real session.
- Profile loading uses the same planner within a transaction. Reference repair and validation of every block complete before the draft is committed.
- Revert returns bytes to the same baseline; the closure remains valid for that baseline.
- Apply failures before writing preserve the draft and ownership. Unconfirmed Apply preserves the draft and locks the session as before.
- Verified Apply initializes a new closure from actual readback. Semantic readback does not establish opaque-byte equality, so the old baseline mask is not carried into a new read.
- Fresh reads, new sessions, JSON/profile restoration, and recovery initialize ownership conservatively from the new baseline. The closure is not exported to JSON, cannot come from external metadata, and grants no live USB authority.

Regression coverage: growth from 1 to 100, a one-shot control case, shrink/grow, interleaved growth of multiple macros requiring relocation/compaction, exact spans with captured anchors, action/device edits during growth, opaque/reserved/flag preservation, reference repair, rollback, profile preview/load/revert/restore, and synthetic actual-readback rebasing.

## R3 — DKS references that must be preserved

After semantic projection, only editable physical positions with DKS bindings matching the incoming profile can authorize template import. For Fn, locked F1–F12 positions are excluded. Locked Fn positions, nonphysical slots, and skipped bindings retain their current dependencies.

If only preserved positions use a template, the incoming profile template is skipped. If editable and preserved positions share a template, changing that template rejects the entire preview/load with its index and conflicting positions. Protected positions never change silently. An unchanged template still permits other edits. A profile may move editable positions to a separate valid index.

Regressions cover every Fn F1–F12 position, slot 127 in both keymap/Fn, shared-template conflicts and unchanged templates, movement to a separate template, and editable base/Fn positions. Failed preview does not change the draft; failed loading preserves the entire draft and diff.

## R4 — Late import read results

Both JSON reading paths share a generation counter. After `await file.text()`, only a request with the current generation and no conflicting transaction may install results or display errors. New imports, entering/leaving sample mode, edit/undo, profile preview/confirm/cancel/library changes, connect/read/disconnect, Apply, and maintenance invalidate older requests. The profile busy gate still prevents overlapping imports within the profile panel; overlapping legacy imports favor the request started later.

Semantic preview is computed before staging changes the generation, so the current request's own errors are not swallowed. A new JSON v1 file can still open in view-only mode after disconnecting an invalidated session; it cannot create an editable/writable session. The recovery queue and model/session checks during saving remain unchanged.

Regressions hold, release, or reject read promises in a controlled order to cover overlapping requests, new sessions, same-session edit/undo, profile preview/confirmation, recovery/library changes, the connection chooser, stale errors, current validation errors, and view-only v1 after invalidation. This is evidence from mocked read scheduling in Node. Real-file browser checks verify ordinary v1/v2/recovery flows; they do not establish reproduction of a slow-read race in the browser.
